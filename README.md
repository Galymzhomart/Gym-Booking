# Gym Booking System — сборка для тестирования

Сборка от 11 ноября 2026 года. Сервер Node.js/Express использует двухфакторный вход Руслана, интерфейс Ернура на казахском, русском и английском и базу Шокана. Темирлан проводит полный прогон по `qa/test_results.csv`.

## 1. Восстановить демо-базу

1. В pgAdmin создай пустую базу `gym_booking_integration`. Используй PostgreSQL 18 для воспроизведения проверенного запуска. Сборка проверена на 18.6. Восстановление на сервере PostgreSQL 17 пока не проверено.
2. Правой кнопкой по новой базе → **Restore**. Укажи `database/backup/gym_booking_test.backup` (Custom). В параметрах исключи восстановление владельцев и привилегий (No owner, No privileges). Права ниже будут выставлены скриптами.
3. Восстановленная копия уже содержит 30 участников, 6 тренеров, 40 занятий и 25 броней. Скрипты `demo_seed.sql` и `demo_seed_extra.sql` в комплекте описывают происхождение данных. Для этого бэкапа переходи сразу к следующему разделу.

## 2. Применить SQL

Открой **Query Tool новой базы** от имени владельца или postgres. Открывай файлы из `database/migrations/` по одному и выполняй **F5**. При SQL-ошибке проверь результат перед следующим файлом.

| Порядок | Файл |
|---|---|
| 1 | `migration.sql` |
| 2 | `migration_delta.sql` |
| 3 | `01_booking_rules.sql` |
| 4 | `02_booking_lifecycle.sql` |
| 5 | `03_translations.sql` |
| 6 | `migration_2fa.sql` |
| 7 | `permissions.sql` |
| 8 | `permissions_additions.sql` |
| 9 | `permissions_2fa.sql` |
| 10 | `app_sessions.sql` |
| 11 | `03b_grants_translations.sql` |

Для теста на своём компьютере выполни `database/seeds/prepare_demo_snapshot.sql`. Он задаёт известные пароли вымышленным аккаунтам из бэкапа и сдвигает устаревшие занятия S-201…S-206, сохраняя их пересечения и соседство.

Затем выполни `database/migrations/enroll_2fa.sql`. В результате появится ключ для каждого демо-аккаунта. В аутентификаторе добавь аккаунт вручную, используя этот ключ и тип «по времени». Для проверки двух ролей достаточно `ayan` и `reception1`. Повторный запуск скрипта заменяет ключи. Ключи остаются в локальной среде.

У роли `gym_app` на том же сервере можно использовать уже заданный пароль. На новом сервере задай собственный пароль для этой роли. У одной роли PostgreSQL один пароль на весь сервер, поэтому изменение пароля повлияет и на другие локальные приложения, использующие её.

## 3. Запустить приложение

В папке с `package.json` открой CMD:

```bat
copy .env.example .env
notepad .env
```

Укажи `DB_NAME=gym_booking_integration`, пароль `gym_app` и собственный новый `SESSION_SECRET`. Для случайного значения секрета можно выполнить `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Новый секрет отделяет сессии тестовой сборки от старого входа без 2FA.

```bat
npm ci
npm start
```

Открой `http://localhost:3000/api/health`. Ожидается `ok: true`, пользователь `gym_app` и имя новой базы. Затем открой `http://localhost:3000`.

## 4. Демо-аккаунты и примеры

| Логин | Пароль после подготовки | Назначение |
|---|---|---|
| `ayan` | `Member#Demo1` | Участник, свободный слот S-301 |
| `reception1` | `Reception#Demo1` | Ресепшен, отметка посещения B-302 |
| `dana` | `Member#Demo2` | Второй участник для проверок доступа |
| `amina` | `Member#Demo3` | Просроченный абонемент |
| `member302` | `Member#Demo4` | Абонемент заканчивается до S-301 |

S-302 занят бронью B-301. B-302 относится к завершённому занятию и доступна для отметки посещения. Используй отдельные восстановленные копии для полного прогона и защиты, чтобы проверка не израсходовала демо-сценарий.

## 5. Статус проверок

- Исходный бэкап Шокана восстановлен в PostgreSQL 18.6. Количество записей совпало с ожидаемым, все семь проверок из `verify_2fa_restore.sql` дали true после установки схемы и прав.
- HTTP-прогон с реальной базой прошёл. Проверены вход участника и ресепшена, отказ до второго фактора, перевод залов и отказа в занятой тренировке на трёх языках, свободный и занятый слот, создание и чтение брони, отмена, повторная бронь, отказ по сроку абонемента, ограничения ролей и отметка посещения.
- Проверки интерфейса в браузере и полный независимый прогон 20 сценариев остаются за Темирланом. Локальный Chromium не запустился из-за запрета на создание Unix-сокета в среде проверки.
- Бэкап в архиве — исходная демо-копия. Для финальной сдачи Шокан создаёт бэкап общей базы и проверяет восстановление. При экспорте общей базы исключи данные `app_user_totp` и `app_sessions`, затем подключи 2FA заново локально.
